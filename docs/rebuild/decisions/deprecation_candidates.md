# Deprecation / Deletion Candidates (Phase 0 inventory)

Scope and stance. This is a Phase-0 behavior-pinning inventory, not a deletion plan. Nothing here is recommended for immediate removal. Each row is a candidate surfaced by the discovery corpus (`deprecation_signals` across slices, plus a few `known_bad` parked-experiment notes). The corpus is the behavioral oracle but not automatically correct; several of these candidates are "parked, not dead" (still tested, still gated, still documented) and a rewrite that drops them without pinning the listed behavior would sever something live.

How to read confidence. `low` = single weak signal, likely keep. `medium` = multiple signals but a live edge or a real edge case is plausible. `high` = strong, multi-form evidence the surface is inactive or redundant, but removal still needs an owner decision and a pin first. No candidate is `confirmed-dead`.

Two cross-cutting cautions before any of the per-candidate work:
- Three load-bearing scars cited below are confirmed by direct read: the unused `_query_hkex_pack` shim (financials.py:1932-1941), the `_STALENESS_YEARS = {}` empty extension hook (financials.py:64), and the production-reads-`tests/fixtures` path (financials.py:1975-1987). The fixture-in-production-path scar is itself a deletion candidate but is currently load-bearing for offline HK demos and `test_cli_json_contract.py`.
- The largest parked surface (FastAPI Evidence Explorer workspace + `web/` Next.js app) is explicitly declared parked by the maintainer (`docs/china-lens/IMPLEMENTATION_TRACKER.md`, beads closed wontfix 2026-04-20) yet is still git-tracked, gated (`SYMPHONY_WEB=1`), and covered by `test_china_api.py` / `test_api_exports.py`. Parked is not dead.

## Notes

### Parked-not-dead: the largest cluster
Candidates 18, 19, 20, and the China LLM fallback (28) form one parked product surface, the China Lens Evidence Explorer web stack. The maintainer's own tracker (`docs/china-lens/IMPLEMENTATION_TRACKER.md`) is unambiguous: the CLI China path (HKEX query, `build-sse`, `translate-sse`) is active; the FastAPI workspace + Next.js frontend are parked, with the corresponding beads closed wontfix 2026-04-20. The decisive feature of these candidates is that they are still tracked, still gated behind `SYMPHONY_WEB=1`, and still covered by tests (`test_china_api.py`, `test_api_exports.py`, `smoke-assets.sh`, `test_repo_layout.py:32`). A rewrite must make an explicit product call ("is China Lens a web product in vNext?") rather than treating the absence of recent commits as a deletion signal. The static-site generator (`edgarpack site`) is the only fully-tested, offline, deterministic web surface and is a natural carry-forward if the FastAPI/Next.js stack is retired.

### Confirmed load-bearing scars that are themselves candidates
- The production-reads-`tests/fixtures` path (financials.py:1975-1987, read-confirmed) is a deletion candidate but is currently the only offline HKEX query path for the `minimax`/`zhipu` demos and is required by `test_cli_json_contract.py`. It also assumes CWD is the repo root. Removing it without a config-driven China pack root would break the offline JSON-contract tests. This is a "fix-then-delete," not a clean removal.
- `_STALENESS_YEARS = {}` (candidate 8, read-confirmed empty) and the `headcount_text.py` private aliases (candidate 10, read-confirmed) are the cheapest, lowest-risk cleanups in this list, but each still needs a grep for patchers/internal references first.

### Two redundant-metric-system candidates worth resolving together
Candidate 6 (`metric_map.py`, the AccountingStandard-keyed map) overlaps conceptually with the live `concepts.py` `MetricMeta` map. `financials.py` imports from `concepts`, not `metric_map`. If `metric_map.py` is still consumed only by the china/hk/comps standard-detection paths, the rewrite should decide whether the standard-keyed map and the `MetricMeta` map should be unified into a single source of truth. This is the single largest "two systems doing one job" signal in the resolution layer.

### Determinism-relevant candidate (decision, not deletion)
Candidate 26 (the tiktoken `len//4` fallback) is not safely removable; it is the resilience path that keeps the package usable offline. But it is also the documented root of non-byte-stable `chunks.ndjson` across environments (BACKLOG item 4). The owner decision is a determinism-policy call: declare tiktoken a hard precondition (and drop the fallback) versus keep it as a supported, explicitly-non-byte-stable mode. Either choice should be pinned in the parity corpus.

### Dead/redundant contract fields (low-risk, documentation-coupled)
Candidates 7 (`source='user'`), 15 (`error_stage`), and 25 (`DistillBundle.warnings`) are all "documented in two places, written by nothing" fields. Each is safe-to-drop behaviorally but is part of a documented JSON/registry shape, so removal changes an external contract. Group them into a single "prune dead contract fields" decision with Samay rather than deciding piecemeal.

### What was deliberately NOT listed as a deletion candidate
Several `deprecation_signals` entries in the corpus were flagged as keep-or-consolidate, not remove: `_synthetic_sse_company` (candidate 23, actively used), `RegistrationProfile.has_content` (candidate 24, under-tested not dead), and `pick_snapshot_fact` (candidate 30, possibly-intentional duplication). They appear here for completeness with an explicit "keep" or "add test" disposition so the rewrite does not mistake an under-tested live branch for dead code.

### Out of scope as a source
`docs/archive/internal/superpowers/` (the parked 2026-04-24 vNext clean-rewrite plan) is itself a parked artifact, but it is inventoried in the docs/history slice, not here, and none of its architectural conclusions inform this list. This deprecation inventory is derived only from current code, tests, and the maintainer's own `IMPLEMENTATION_TRACKER.md` / `BACKLOG.md`.
