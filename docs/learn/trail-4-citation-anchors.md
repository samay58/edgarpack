# Trail 4: How a number gets a deep-link URL back to the filing

**Time**: ~10 minutes
**Prereq**: [Trail 0](trail-0-full-loop.md). You should know how `financials()` calls `select_period` and returns a `QueryResult`.
**Covers**: `query/financials.py` (enrichment pass), `query/periods.py` (fact_id parsing), `query/models.py` (URL builders)

Every value in a query result carries more than the filing it came from. When the
source filing supports it, EdgarPack also builds a URL that lands on the exact
inline XBRL fact in the HTML. Producing that URL takes two passes through the
data and one tour of inline XBRL.

---

## 1. Why fact IDs exist

When the SEC publishes an inline XBRL filing, every financial fact in the HTML carries an `id` attribute on its `<ix:nonFraction>` tag. The ID is opaque, something like `id="f-47"` or `id="fact-abc123"`. It's generated by whatever tool the filer used to produce the XBRL; EdgarPack never interprets the format, just copies it.

The point of the ID is that you can append `#f-47` to the filing's HTML URL and modern browsers will scroll directly to that element. No text-fragment needed, no JavaScript viewer, no SEC viewer wrapper. It's a plain HTML anchor.

This is why EdgarPack goes to the trouble of parsing inline XBRL a second time after it already has the values from companyfacts. Companyfacts gives you the number; the fact ID gives you the link.

---

## 2. The enrichment pass is separate from value resolution

If you read `financials.financials()` at `edgarpack/query/financials.py:664` end to end, you'll notice that fact ID enrichment is the last thing it does, after the metrics loop, after the low-debt sanity check, after building the `QueryResult`:

```python
result = QueryResult(company=company_name, cik=cik, period=period, metrics=result_metrics)

accessions = _collect_accessions(result)
if accessions and doc_map:
    fact_id_maps = await _fetch_fact_id_maps(cik, doc_map, accessions)
    _enrich_fact_ids(result, fact_id_maps)

return result
```

Three functions, all in `financials.py`: `_collect_accessions` gathers the set of unique accession numbers in the result, `_fetch_fact_id_maps` fetches each filing's HTML and parses the fact IDs, `_enrich_fact_ids` walks the result again and writes the IDs back into each `CitedValue`.

The separation is a cost optimization. Doing enrichment inline with value resolution would mean a fetch per value. Batching it means a fetch per unique filing, usually 1-3 for a typical query. For an LTM query that touches three filings (MRP, LFY, MRP_prior), the enrichment pass is exactly three fetches no matter how many metrics you asked for.

**Code**: `edgarpack/query/financials.py:1093-1107` (the three-line enrichment block)

## 3. Collect accessions

`_collect_accessions` at `edgarpack/query/financials.py:244` walks the `QueryResult` and pulls every accession it finds:

```python
def _collect_accessions(result: QueryResult) -> set[str]:
    accessions: set[str] = set()
    for v in result.metrics.values():
        if v is None:
            continue
        items = v if isinstance(v, list) else [v]
        for item in items:
            if item.accession:
                accessions.add(item.accession)
            if isinstance(item, DerivedValue):
                for comp in item.components.values():
                    if comp.accession:
                        accessions.add(comp.accession)
    return accessions
```

Two things worth pointing out:

1. Series queries (`annual:N`, `quarterly:N`) return lists, so the loop has to handle both scalar `CitedValue` and `list[CitedValue]` shapes. `isinstance` handles that.
2. For `DerivedValue` results (LTM, ebitda, margins), the enrichment goes one layer deeper into `components`. Each component is itself a `CitedValue` with its own accession. All of them get enriched.

The output is a set. Duplicate accessions are deduped here before any HTTP calls are made.

## 4. Fetch and parse fact IDs

`_fetch_fact_id_maps` at `edgarpack/query/financials.py:208` runs one async fetch per unique accession, in parallel:

```python
async def _fetch_one(accn: str) -> None:
    primary_doc = doc_map.get(accn, "")
    if not primary_doc:
        return
    meta = FilingMeta(
        cik=cik_bare,
        accession=accn,
        form_type="",
        filing_date=_date.min,
        primary_document=primary_doc,
        company_name="",
    )
    try:
        html_bytes = await fetch_file(meta, primary_doc)
        result[accn] = parse_fact_ids_from_html(html_bytes)
    except (HTTPError, OSError, ValueError) as e:
        logger.warning("fact_id map fetch failed for %s: %s", accn, e)

await asyncio.gather(*[_fetch_one(accn) for accn in accessions])
```

The `FilingMeta` is built with stub values for the fields that aren't needed. `form_type`, `filing_date`, and `company_name` all get defaults because `fetch_file` only uses `cik`, `accession`, and the filename argument. It's a bit of an API smell but it's internal, and the alternative is plumbing a new fetch signature through `sec/archives.py`.

The fetch itself goes through the cached `fetch_file` path from Trail 2. Every filing HTML is already cacheable indefinitely (SEC filings don't change once published), so subsequent queries on the same filings hit the cache instead of re-fetching.

If a fetch fails, the warning is logged and the failed accession is absent from the result dict. Downstream code treats "no fact_id map" the same as "no fact_id found"; both flow into the fallback URL path.

## 5. The inline XBRL parser

`parse_fact_ids_from_html` at `edgarpack/query/periods.py:73` is a regex-based parser that extracts `(concept, value) -> fact_id` mappings from inline XBRL HTML.

```python
_IX_NONFRACTION_TAG_RE = re.compile(
    r"<ix:nonFraction\b([^>]*)>([^<]*)</ix:nonFraction>",
    re.IGNORECASE | re.DOTALL,
)
```

The pattern captures the attribute blob and the inner text of every `<ix:nonFraction>` element. For each match the parser:

1. Extracts `name="..."` -> concept (e.g. `us-gaap:Revenues`)
2. Extracts `id="..."` -> fact_id (e.g. `f-47`)
3. Extracts `scale="..."` and `sign="..."` attributes (both optional)
4. Strips the taxonomy prefix from the concept: `us-gaap:Revenues` -> `Revenues`
5. Parses the display text into a float via `_parse_display_value` at `edgarpack/query/periods.py:39`: strip commas, handle parentheses for negative numbers (then apply the `sign` attribute which is authoritative), apply the `scale` multiplier (XBRL reports numbers in units like thousands/millions via `scale="6"` meaning x10^6).
6. Stores the result: `{(concept_short, scaled_value): fact_id}`

The composite key `(concept, value)` is what makes this work. Within a single filing, the same concept at different periods almost always has a different dollar value. Revenue for 9 months Q3 2024 is a different number from revenue for 3 months Q1 2024. The tuple is a reliable unique key in practice.

The parser also handles a rare edge case: duplicate `(concept, value)` pairs from the notes section repeating values from the financial statements. First-occurrence-wins (line 104) means the financial statement element (which appears earlier in the HTML) keeps its fact_id.

**Code**: `edgarpack/query/periods.py:39-64` (`_parse_display_value`), `edgarpack/query/periods.py:73-107` (`parse_fact_ids_from_html`)

## 6. Write the IDs back

`_enrich_fact_ids` at `edgarpack/query/financials.py:261` walks the result one more time and writes each discovered fact_id into the corresponding `CitedValue`:

```python
def _enrich_one(cited: CitedValue) -> None:
    if cited.fact_id:
        return  # Already set
    fmap = fact_id_maps.get(cited.accession)
    if fmap:
        cited.fact_id = _lookup_fact_id(fmap, cited.concept, cited.value)
```

`_lookup_fact_id` at `edgarpack/query/periods.py:116` strips the taxonomy prefix from the concept (same rule as the parser) and looks up `(concept_short, float(val))` in the map. If found, returns the fact_id string; if not, returns empty string.

The result is that `cited.fact_id` is now populated for every value the parser found. Any value not found (either because the parser missed it, or because it came from a filing whose HTML fetch failed) keeps its empty-string default, which is how the fallback path works.

## 7. The URL builders on `CitedValue`

With `fact_id` possibly populated, the `CitedValue.anchor_url` property at `edgarpack/query/models.py:155` can build the actual deep-link URL:

```python
@property
def anchor_url(self) -> str | None:
    if not self.fact_id or not self.primary_document:
        return self.document_url
    acc_nodash = self.accession.replace("-", "")
    cik_bare = self.cik.lstrip("0")
    base = f"{SEC_ARCHIVES_BASE}/{cik_bare}/{acc_nodash}/{self.primary_document}"
    return f"{base}#{self.fact_id}"
```

If `fact_id` is present, the URL is `.../primary.htm#f-47`, a plain HTML anchor that works in every browser.

If `fact_id` is missing, `document_url` at `edgarpack/query/models.py:130` kicks in as fallback:

```python
@property
def document_url(self) -> str | None:
    if not self.primary_document:
        return None
    acc_nodash = self.accession.replace("-", "")
    cik_bare = self.cik.lstrip("0")
    base = f"{SEC_ARCHIVES_BASE}/{cik_bare}/{acc_nodash}/{self.primary_document}"
    label = _concept_to_label(self.concept)
    return f"{base}#:~:text={quote(label)}"
```

This builds a Chrome/Edge text-fragment URL (`#:~:text=...`) using the concept name transformed from camelCase to space-separated via `_concept_to_label` at line 14. Clicking it scrolls the browser to the first occurrence of the concept label on the page. Worse than the fact_id anchor (the label might match in the wrong place; text fragments don't work in Safari), but better than just linking to the top of the filing.

If `primary_document` is also missing, the URL is `None`. The citation will only have the filing-level URL (`.../accession-index.htm`) which takes the reader to the filing landing page.

**Code**: `edgarpack/query/models.py:82-169` (all URL builders)

## 8. Other URLs on the same object

While we're here, the model exposes a few other URLs that downstream formatters can use:

- `filing_url` (line 48): the filing's SEC index page (`.../accession-index.htm`). Always available; derived from accession and CIK only.
- `concept_url` (line 53): the SEC companyconcept API URL for the full historical series of this concept. Returns `None` for derived metrics (the "concept" for EBITDA is the formula string, not a GAAP tag).
- `viewer_url` (line 67): the SEC Inline XBRL Viewer URL (`https://www.sec.gov/ix?doc=...`). This opens SEC's own viewer with XBRL facts highlighted. Requires `primary_document`.

The CLI's `_render_query_table` at `edgarpack/query/render.py:140` picks between these based on `--show-links` flag: `primary` uses `anchor_url` (fact_id or text-fragment), `all` shows filing + anchor + viewer, `none` shows the citation text without any URL.

---

## Recap

Citation anchors take two passes because doing them inline would waste HTTP calls on a value-by-value basis. The first pass resolves metric values through companyfacts and builds a `QueryResult` with provenance fields (accession, primary_document). The second pass walks the unique accessions, fetches each filing's HTML once, parses the inline XBRL for `(concept, value) -> fact_id` mappings, and writes the IDs back into the existing `CitedValue`s. The `anchor_url` property on `CitedValue` then assembles the final link, falling back to a text-fragment URL if no fact_id is available, and falling further back to the filing-level URL if even the primary document is missing. Every number in the final output carries enough metadata to reach the exact span of HTML that produced it, or the best approximation available. That's the contract the README is talking about. The whole thing is about 150 lines of code split across three files. Most of the complexity lives in the inline XBRL parser (40 lines of regex plus a value formatter), and the load-bearing move is using `(concept, value)` as a composite key so the parser doesn't need to understand XBRL contexts.
